# v1.1 Milestone Audit - Remote RE Tool Expansion

**Audited:** 2026-05-20  
**Scope:** `.planning` milestone artifacts for v1.1, phase artifacts 05-12, gateway implementation, orchestrator skill copies, and host-runnable non-slow gateway tests.

## Verdict

**Not ready to archive.**

The implementation has substantial v1.1 functionality in place, but milestone completion is not currently defensible because:

- the full non-slow gateway test suite is red;
- four phases remain `human_needed` with pending UAT;
- the Codex orchestrator skill copy is stale relative to the Claude copy;
- resource caps for sessions/jobs have TOCTOU races under concurrent opens/submits;
- the r2 dangerous-command denylist still has known bypass forms;
- top-level `.planning` status files disagree about completion.

## Findings

### BLOCKER 1 - Full non-slow suite is not green

Phase 9 verification claimed a full gateway non-slow pass while ignoring/preceding later job-spec additions. The current full non-slow suite fails in the Phase 9 jobs tests after Phase 10/11 extensions.

**Impact:** the milestone cannot be archived as passing CI/verification until the full intended suite is green or the host-only/container-only split is made explicit and enforced by markers.

**Route:** update the Phase 9 job-spec tests to account for Phase 10/11 registered specs, and decide whether `test_acl_available.py` should remain a host fail-loud test or become a container-only check.

### BLOCKER 2 - Codex malware orchestrator skill is stale

Project instructions require shared analysis skills to keep Claude and Codex copies synchronized. They are not synchronized:

- `workspace/.codex/skills/malware-analysis-orchestrator/SKILL.md` still says Binary Ninja is primary and Ghidra secondary.
- `workspace/.claude/skills/malware-analysis-orchestrator/SKILL.md` has the v1.1 IDA-first backend priority and W-1..W-7 workflow routing.
- Codex is missing `references/deep-re-workflows.md`, the entire `references/workflows/` directory, and `scripts/probe_dynamic_tools.sh`.
- Codex `references/artifact-spec.md` lacks the v1.1 `mode`, `dynamic_mode_enabled`, and `dynamic_capabilities` fields.

The regression test only targets `workspace/.claude/skills/malware-analysis-orchestrator`, so this drift is untested.

**Impact:** Codex agents will follow stale v1.0/v1.0-era workflow guidance and miss the v1.1 tool surface.

**Route:** sync the Codex skill copy from the Claude source, preserving Codex-specific wording where agent identity matters, and add a regression test that detects future Claude/Codex drift.

### BLOCKER 3 - Required human UAT is still pending

The phase verification artifacts still mark these phases as `human_needed`:

- Phase 7: container `mare-shell`/ACL checks, 100 MB run_shell test, live MCP resources roundtrip.
- Phase 8: in-container r2-gated tests and zombie-free r2 shutdown.
- Phase 10: recursive extraction/promotion UAT, archive-bomb cap, probe script, slow extraction tests.
- Phase 11: live dynamic tool count, strace/qemu/gdb in-container tests, dynamic probe READY verdict.

The matching `*-HUMAN-UAT.md` files are all `status: partial` with all listed tests pending.

**Impact:** v1.1's highest-risk runtime behavior has not been validated in the actual Kali/container environment.

**Route:** run the pending container/live-client checks, record results in the HUMAN-UAT files, and only then move the milestone toward archive.

### HIGH 1 - Session cap is bypassable under concurrent opens

Both r2 and gdb session creation check the cap under a lock, release the lock for spawn/init work, then insert the session later:

- `mcp-gateway/src/mcp_gateway/sessions/r2.py`: cap check around lines 130-134, insertion around lines 220-222.
- `mcp-gateway/src/mcp_gateway/sessions/gdb.py`: cap check around lines 300-304, insertion around lines 413-415.

The existing tests cover serial N+1 opens, not concurrent `asyncio.gather` opens.

**Impact:** an authenticated client can exceed `MCP_GATEWAY_MAX_SESSIONS` by racing concurrent opens, potentially exhausting RAM/PIDs with r2/gdb subprocesses.

**Route:** reserve a pending session slot under the lock before spawning, remove it on failure/cancellation, and add concurrent cap regression tests for r2 and gdb.

### HIGH 2 - Background job cap has the same TOCTOU pattern

`BackgroundJobRegistry.submit()` checks `_inflight` under a lock, releases the lock while building argv/log paths, then inserts the job under a second lock.

**Evidence:** `mcp-gateway/src/mcp_gateway/jobs.py` cap check around lines 549-556, insertion around lines 575-577.

**Impact:** concurrent `start_tool_job` calls can exceed the intended in-flight cap.

**Route:** insert a placeholder job under the same lock as the cap check, backfill argv/log fields after validation, and remove the placeholder on failure.

### HIGH 3 - r2 dangerous-command denylist has known bypass forms

The r2 deny regex currently blocks `#!`, `R!`, and `!` only at start/`;`/pipe/newline boundaries. Phase 8 review already documented bypasses such as backtick substitution and dot-shell-eval (`.!cmd`), and the source still matches the reviewed pattern.

**Impact:** `r2_cmd` can potentially reach shell escape behavior despite SESS-06's dangerous-command refusal requirement.

**Route:** replace the fragile regex with token/structural parsing, or at minimum expand the regex and test matrix for backticks, `.!`, and nested shell forms.

### MEDIUM 1 - `follow_fork_mode` is accepted but not applied

`open_gdb_session()` validates `follow_fork_mode`, but does not pass it into `registry.open()`. `_open_gdb()` defaults to `parent`, and the lockdown batch always includes `-gdb-set follow-fork-mode parent`.

**Impact:** callers requesting `follow_fork_mode="child"` receive a session that still follows the parent.

**Route:** pass the option through the registry/open driver and generate the matching lockdown line from the requested value.

### MEDIUM 2 - Planning status is internally inconsistent

Examples:

- `STATE.md` frontmatter says v1.1 is 100% complete, but the visible "Current Position" still says Phase 12 "Not started" and progress 0%.
- `ROADMAP.md` still has Phase 5-9 unchecked and the progress table still says those phases are "Not started".
- `REQUIREMENTS.md` still leaves SHELL-03 and ARTIF-01..04 unchecked, and the traceability table says every v1.1 requirement is `Pending`.
- Several `*-VALIDATION.md` files still have draft/false frontmatter despite corresponding verification reports claiming pass.

**Impact:** future agents cannot reliably determine whether v1.1 is complete, pending verification, or blocked.

**Route:** after fixing the blockers, update `.planning/ROADMAP.md`, `.planning/REQUIREMENTS.md`, `.planning/STATE.md`, and stale validation frontmatter in one consistency pass.
